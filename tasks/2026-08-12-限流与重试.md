## 任务 1：@RateLimit 限流注解 + 切面

### 1.1 annotation/RateLimit.java
```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    int limit();                    // 窗口内最大次数
    int windowSeconds() default 60; // 窗口秒数
    String key() default "";        // 可选，SpEL 或固定字符串；为空时默认 = IP + 类名.方法名
}
```

### 1.2 aspect/RateLimitAspect.java
- `@Aspect @Component @Slf4j @RequiredArgsConstructor`
- 注入 `StringRedisTemplate`（注意：项目里 RedisTemplate 是 `RedisTemplate<String, Object>`，StringRedisTemplate 是独立 bean，直接注入即可）
- `@Around("@annotation(rateLimit)")`
- key 生成：
  - 注解 key 非空 → 原样使用（不做 SpEL，避免复杂化；固定字符串如 "admin:coupon-batch" 即可）
  - 为空 → `RequestContextHolder` 取 remoteAddr（无请求上下文则 "unknown"）+ ":" + 类名.方法名
- Redis Lua 固定窗口计数（原子）：
  ```java
  DefaultRedisScript<Long> script = new DefaultRedisScript<>(
      "local c = redis.call('INCR', KEYS[1]); if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end; return c",
      Long.class);
  Long count = stringRedisTemplate.execute(script, List.of(lockKey), String.valueOf(rateLimit.windowSeconds()));
  ```
- 计数 > limit → 抛 `com.homestay3.homestaybackend.exception.RateLimitExceededException`（新建，RuntimeException 子类，message 如"请求过于频繁，请稍后再试"）
- **Redis 不可用/执行异常 → 降级放行**（log.warn + 直接 proceed，与项目 RedisLock 的降级原则一致）
- 切面自身异常处理：只允许 RateLimitExceededException 向外抛，其他异常吞掉放行

### 1.3 全局异常处理
exception/GlobalExceptionHandler.java 加：
```java
@ExceptionHandler(RateLimitExceededException.class)
public ResponseEntity<Map<String, Object>> handleRateLimit(RateLimitExceededException e) {
    return ResponseEntity.status(429).body(Map.of("success", false, "message", e.getMessage()));
}
```
（返回 429 + message；保持现有 Map 响应风格）

### 1.4 调用点（加在 Controller 写接口上，2 处）
1. `AdminPromotionController` 创建批量发券任务的方法（POST，路径含 batch-tasks 的）：`@RateLimit(limit = 5, windowSeconds = 60, key = "admin:coupon-batch")`
2. `PaymentController` 创建支付订单的方法（POST 创建支付那个）：`@RateLimit(limit = 30, windowSeconds = 60)`（默认 key=IP+方法）

### 1.5 单元测试（新建 src/test/java/.../aspect/RateLimitAspectTest.java）
纯 Mockito（参考现有 RedisLockAspectTest 的写法，不依赖 Spring 上下文/数据库）：
- 计数未超限 → 业务方法执行
- 计数超限 → 抛 RateLimitExceededException，业务方法不执行
- Redis 执行异常 → 降级放行，业务方法执行
（mock StringRedisTemplate.execute 返回值；测试方法用 @RateLimit 注解 + 反射取注解）

### 2.3 LlmClient.chat 加重试
文件：service/agent/LlmClient.java（@Service，已是 Spring bean）
- **先读 chat 方法完整实现**，确认异常流：restTemplate.exchange 抛的 RestClientException 是被 catch 后转成 AgentLlmException 还是原样抛出？
- 目标：**只对网络/超时类失败重试**（连接超时、读超时、5xx 等瞬时故障），不对响应解析失败重试
- 实现方式（二选一，以异常流为准）：
  - 若 RestClientException 原样抛出：`@Retryable(value = RestClientException.class, maxAttempts = 3, backoff = @Backoff(delay = 1000, multiplier = 2))`
  - 若被转换为 AgentLlmException：`@Retryable(value = AgentLlmException.class, maxAttempts = 3, backoff = @Backoff(delay = 1000, multiplier = 2))`（前提：AgentLlmException 只包装网络类失败；若解析失败也抛它，则需要在 catch 处区分——把网络失败抛 AgentLlmException、解析失败抛原样 RuntimeException）
- 重试 3 次（1 次初始 + 2 次重试），指数退避 1s → 2s
- 重试耗尽后照旧抛出（上层 SupportAgentServiceImpl / DisputeAdvisorServiceImpl 已有降级逻辑，不要动它们）
- **不要动** chat 方法内部业务逻辑，只加注解/调整异常转换
