边界、分支与代码入口

主图包含九个节点，折叠每个工具和模型内部调用；展示当前代码流程，不假设模型具有数据库权限。七个只读工具与三个起草工具在注册表硬编码，总计十个；不注册批准退款、押金处置或仲裁等操作。

会话敏感词直接返回人工标志；内存会话计数 TTL 一小时，第 4 轮起转人工。LLM 或编排异常也返回人工标志。handoff 当前返回响应和提示，核对入口未见真实人工客服分配或通知调用。

决策采用 JSON 文本协议，允许多跳调用直到 need_tool 为 false、解析降级或 maxToolHops 上限。不是原生 function calling。每次工具结果写入 toolTrace 后重新决策；回答轮根据这些结果生成回复。

未注册工具、越权和工具错误被转为工具结果文本供回答轮使用，不一定直接转人工。订单相关工具在各自实现中使用 OrderAccessGuard；公开房源、评价和报价工具不能笼统画成全部需要订单归属校验。

三个写工具只返回 pendingAction（操作、订单、原因、摘要），不执行业务写入。多跳中后一个 pendingAction 可覆盖前一个，响应最终携带一个确认动作。没有 pendingAction 的回答不会进入确认链。

用户取消只移除前端卡片；确认请求 POST /api/support/agent/confirm 才分发申请退款、取消订单或发起争议。后端重新校验订单客人和必要参数，业务 Service 再检查状态。确认接口不是自动批准退款。

pendingAction 来自前端请求体；当前确认流程没有服务端保存草稿、签名绑定或一次性消费 token，不能宣称确认内容不可变或天然幂等。失败时前端保留卡片，成功后移除。

管理员争议建议走独立 DisputeAdvisorService：订单时间线、聊天摘要、相似案例 → LLM 建议草稿；模型失败降级返回材料。它不执行仲裁，不是房客工具循环的下一步。
