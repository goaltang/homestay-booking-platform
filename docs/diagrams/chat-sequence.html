聊天通过 HTTP 写入、事务内 WebSocket 推送和 HTTP 历史查询实现；该链路与 MQ 通知场景不同。

阅读说明与范围

前端经 POST /api/chat/conversations/{id}/messages 发送消息；Controller 从认证身份取 userId 并检查非空内容。服务保存消息、会话最后一条摘要和接收方未读数。

ChatServiceImpl.sendMessage 的事务尚未返回时，直接调用 WebSocketService：向 /topic/chat/{conversationId} 和 /topic/chat/user/{receiverId} 两个主题发送。不是 afterCommit，也没有走本项目通知 MQ 重试队列。

推送异常被 WebSocketService 捕获并记录，不等于聊天请求失败，也不保证客户端收到。推送可能先于最终事务提交；客户端显示不能作为落库成功的证明。图中省略网络返回时间差及客户端事件去重细节。

打开会话时前端请求历史消息并标记已读；标记已读更新对方发出的消息与当前用户未读数。未读接口统计有未读消息的会话数量，不等于所有未读消息条数。

当前静态核对发现：ChatController 要求已登录，但 ChatServiceImpl 的 getConversation、getMessages、sendMessage、markMessagesAsRead 未见会话参与者归属检查；图中不添加不存在的权限 Guard。WebSocket 订阅授权未在本图审计。

本图只记录实现和限制，没有修改聊天业务，也未执行双客户端实时联调。
