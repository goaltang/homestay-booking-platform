边界、分支与代码入口

三列是创建、支付成功、后续处理；最后一列合并取消、退款与履约的不同分支，并非所有订单都会依次经历这些动作。图中九个节点对应选定状态与处理，不是全部合法状态迁移表。

OrderStatusUpdater 将订单状态和 PaymentStatus 配对更新：待确认/确认与支付中通常为 UNPAID；支付、入住和完成为 PAID；申请退款为 REFUND_PENDING；退款完成为 REFUNDED；争议为 DISPUTED。

下单时锁定用户券，扣减活动预算并写 LOCKED 使用流水；同时写入价格快照。未选券、未匹配活动的订单没有这些资源变化。锁券失败会抛出异常，下单外层事务回滚。

handleOrderPaidSuccess 要求订单为 PAID，尝试锁券核销与活动流水 USED；异常单独捕获。因此订单已支付不能作为优惠核销完成的证明，图中虚线表达有条件的后置处理。

取消相关路径调用 releaseCoupons，只将 LOCKED 券恢复 AVAILABLE，已经 USED 的券不会被这个 SQL 恢复。活动流水在该调用处按当时 PaymentStatus 是否为 PAID 选择 REFUNDED 或 RELEASED；这不是单纯依据订单终态判断。相关异常被捕获，预算回退 false 未见处理。

直接 requestUserRefund 路径不等同 cancelOrderWithReason 路径；管理员 executeRefund 有单独的券释放尝试，不能给所有退款入口统一承诺券、预算都恢复。预算回退也不自动恢复已 ENDED 活动。

价格快照提供 hostReceivableAmount，收益生成优先使用快照，缺失时按订单金额与房东分成计算。支付成功和退房确认都可能触发生成；查找已有订单收益后复用，生成失败可以不阻止主流程。

收益初始 PENDING；settleHostEarnings 将该房东当前 PENDING 记录改为 SETTLED，没有按退房日期过滤，也没有资金转账。退款后的收益自动冲销未在这些核对入口中见到，不画自动闭环。

取消后日期库存释放、退款与本地状态原子一致、争议批准状态冲突等限制仍然存在；本图没有修改业务代码。
