# 文档分类与维护规则

## 每篇文档先确定用途

| 用途 | 目录 | 回答的问题 |
|---|---|---|
| 项目说明 | `01-项目说明/` | 项目是什么、怎样启动 |
| 功能说明 | `02-功能模块/` 对应业务域 | 用户能做什么、业务规则是什么 |
| 技术设计 | `03-技术设计/` | 机制如何实现、代码在哪里 |
| 验证与复盘 | `04-验证与复盘/` | 如何验证、结果如何、未覆盖什么 |
| 方案 | `05-方案与规划/` | 改什么、如何选、哪些未完成 |
| 学习参考 | `90-学习笔记/` | 通用知识和行业观察 |
| 求职素材 | `99-求职准备/` | 简历与面试表达，本地保留 |

一篇文档只承担一种主要用途。功能说明中不放面试话术；报告不重复完整架构；方案的实施结果单独写复盘并互相链接。

## 信息只维护一份

| 信息 | 权威入口 |
|---|---|
| 完整安装流程 | 仓库 `docs/INSTALL.md` |
| 技术版本 | [[项目技术栈]]，来源是构建与依赖文件 |
| 模块能力与规则 | 对应 `功能模块-*.md` |
| 共享机制 | 对应技术设计；图与实现限制见 `docs/diagrams/README.md` |
| 历史测量数字 | 有日期、环境和方法的原报告 |
| 功能模板 | [[功能模块文档规范]] |

三端概览只介绍职责和入口，不复制技术栈与安装流程。仪表盘说明数据概览，通知规则集中在 [[功能模块-通知中心]]。

## 属性与状态

```yaml
---
title: 文档标题
date: 2026-10-10
type: 功能说明
status: 待核对
updated: 2026-10-10
tags:
  - homestay
---
```

| 属性 | 用途 |
|---|---|
| `date` | 原始记录日期，不能因移动目录改成今天 |
| `updated` | 最近修改日期 |
| `reviewed` | 对照代码的日期，没有核对就不填 |
| `type` | 文档用途 |
| `status` | 文档状态，不是功能完成或测试通过的证明 |
| `aliases` | 文件更名后的旧名称 |

状态含义见 [[00-首页#如何判断一篇文档能否当作当前事实]]。核对要写清范围与代码入口；预期性能与实测分开；历史待办不能直接当作今天的任务。

## 命名与链接

- 功能文件用 `功能模块-{名称}.md`，只描述模块职责。
- 当前技术说明用 `技术设计-{主题}.md`；历史方案保留在历史目录。
- 阶段审查或复盘保留观察时间，如 `复盘-前端代码审查优化-2026-05.md`。
- 笔记间使用 Wikilink；首页、完整目录和仓库 README 使用标准 Markdown 相对链接，兼容 GitHub。
- 跨到仓库代码和 docs 的链接使用相对路径；路径含空格时用尖括号包住目标。
- 更名保留旧名称别名，并修复仓库引用和本地求职笔记的链接。
- `.obsidian/` 工作区与插件配置继续忽略。

## 日常维护

代码变化时更新当前功能说明；测试或排障结束后记录有日期的证据；新想法放方案或任务系统。实施后形成技术说明，原方案按历史记录保留。

新增或重写功能正文遵循 [[功能模块文档规范]]。旧文档本轮保留原信息并标记待核对；改到对应模块时再核对完整正文，不凭整理日期宣称重新验证。
