# 登录认证统一改造方案

> [!info] 结论
> 建议把认证体系收敛为一套用户身份模型：所有登录用户都来自 `users` 表，通过 `ROLE_USER`、`ROLE_HOST`、`ROLE_ADMIN` 区分权限。管理后台可以保留独立登录页面和兼容接口，但底层不再维护独立的管理员账号体系。

## 背景

当前系统看起来有“两套登录系统”，实际分成两类问题：

- **前台重复状态源**：`homestay-front` 同时存在 `useAuthStore` 和 `useUserStore`，两者都维护 `token`、用户信息、登录、注册、退出登录，并分别写入 `localStorage.user` 与 `localStorage.userInfo`。
- **前后台登录边界混用**：`homestay-admin` 走 `/api/admin/auth/login`，后端存在 `admin` 表；普通用户走 `/api/auth/login` 和 `users` 表。但 `CustomUserDetailsService` 又会先查 `users` 表，再查 `admin` 表，启动逻辑还会同步默认 `admin` 到两张表。
- **本地存储键冲突**：前台和管理后台都使用 `localStorage.token`、`localStorage.userInfo`。如果未来同域部署或调试窗口共用域名，容易互相覆盖。
- **安全风险**：`AdminServiceImpl.initializeAdminAndUser()` 启动时可能重置默认管理员密码，不适合作为长期生产逻辑。

## 目标架构

### 身份模型

统一使用 `users` 表作为登录主体。

| 角色 | role | 说明 |
|---|---|---|
| 普通用户 | `ROLE_USER` | 浏览房源、下单、收藏、评价 |
| 房东 | `ROLE_HOST` | 拥有普通用户能力，并可进入房东中心 |
| 管理员 | `ROLE_ADMIN` | 可进入管理后台，访问 `/api/admin/**` |

### 登录入口

| 入口 | 保留形式 | 底层逻辑 |
|---|---|---|
| 用户前台 `/login` | 保留 | 调用统一认证服务，允许 `ROLE_USER`、`ROLE_HOST`、`ROLE_ADMIN` 登录 |
| 管理后台 `/login` | 保留 | 可继续调用 `/api/admin/auth/login`，但接口内部复用统一认证，并强制校验 `ROLE_ADMIN` |
| 后端 `/api/auth/login` | 主入口 | 返回统一的 `AuthResponse` |
| 后端 `/api/admin/auth/login` | 兼容入口 | 登录成功后仅允许管理员，否则返回 403 |

> [!tip] 迁移策略
> 不建议第一步直接删除 `/api/admin/auth/login`。先把它改成兼容入口，等管理后台稳定后，再考虑删除旧的 `admin` 表和旧认证服务。

## 改造阶段

## 第一阶段：前台登录状态统一

目标：先消除 `homestay-front` 内部的重复登录状态。

### 改动范围

- 保留一个 Pinia store 作为唯一认证状态源，建议保留 `useUserStore` 或重命名为 `useAuthStore`。
- 统一字段：
  - `token`
  - `userInfo`
  - `isAuthenticated`
  - `isAdmin`
  - `isHost`
  - `login()`
  - `register()`
  - `logout()`
  - `fetchUserInfo()`
- 停止同时维护 `localStorage.user` 和 `localStorage.userInfo`，统一使用一个键，例如 `homestay_user`。
- 前台 token 键建议改为 `homestay_token`，避免和管理后台冲突。
- 修改路由守卫、请求拦截器、页面组件中对旧 store 的引用。

### 重点文件

- `homestay-front/src/stores/auth.ts`
- `homestay-front/src/stores/user.ts`
- `homestay-front/src/router/index.ts`
- `homestay-front/src/utils/request.ts`
- `homestay-front/src/utils/auth.ts`
- `homestay-front/src/views/Login.vue`
- `homestay-front/src/views/Register.vue`
- `homestay-front/src/layouts/UserLayout.vue`
- `homestay-front/src/views/host/*`

### 验收标准

- 登录后刷新页面，用户状态不丢失。
- 普通用户无法访问房东中心。
- 房东可以正常访问房东中心。
- 退出登录后，token、用户信息、收藏缓存等敏感状态被清理。
- 401 响应只触发一次清理和跳转，不出现循环跳转。

## 第二阶段：管理后台本地状态隔离

目标：避免管理后台和用户前台互相覆盖本地登录状态。

### 改动范围

- 管理后台 token 键改为 `homestay_admin_token`。
- 管理后台用户信息键改为 `homestay_admin_user`。
- `homestay-admin/src/stores/user.ts`、`homestay-admin/src/utils/request.ts`、`homestay-admin/src/router/index.ts` 统一读取新键。
- 登录成功后只保存管理员视角需要的信息，不复用前台 `userInfo`。

### 验收标准

- 同一浏览器中，前台登录用户和后台登录管理员互不影响。
- 管理后台退出登录不会清掉前台用户登录态。
- 前台退出登录不会清掉后台管理员登录态。

## 第三阶段：后端统一认证服务

目标：后端只维护一套用户认证逻辑。

### 改动范围

- `AuthServiceImpl.login()` 作为统一登录逻辑。
- 新增或调整一个管理后台登录方法：
  - 复用 `AuthenticationManager` 验证用户名密码。
  - 验证用户角色必须包含 `ROLE_ADMIN`。
  - 返回管理后台需要的响应结构。
- `AdminAuthController.login()` 改成调用统一认证逻辑，而不是依赖独立 `AuthenticationService` + `AdminRepository`。
- `CustomUserDetailsService` 只从 `users` 表加载用户。
- 保留 `/api/admin/**` 的 `ROLE_ADMIN` 权限控制。
- 移除启动时重置默认管理员密码的逻辑。

### 重点文件

- `homestay-backend/src/main/java/com/homestay3/homestaybackend/controller/AuthController.java`
- `homestay-backend/src/main/java/com/homestay3/homestaybackend/controller/AdminAuthController.java`
- `homestay-backend/src/main/java/com/homestay3/homestaybackend/service/impl/AuthServiceImpl.java`
- `homestay-backend/src/main/java/com/homestay3/homestaybackend/service/AuthenticationService.java`
- `homestay-backend/src/main/java/com/homestay3/homestaybackend/service/CustomUserDetailsService.java`
- `homestay-backend/src/main/java/com/homestay3/homestaybackend/service/impl/AdminServiceImpl.java`
- `homestay-backend/src/main/java/com/homestay3/homestaybackend/config/SecurityConfig.java`

### 验收标准

- `ROLE_ADMIN` 用户可以登录管理后台。
- 非管理员用户调用 `/api/admin/auth/login` 返回 403 或明确的权限错误。
- 管理后台接口 `/api/admin/**` 继续要求 `ROLE_ADMIN`。
- 普通用户、房东登录不受影响。
- JWT 中包含稳定的 `userId`、`username`、`authorities`。

## 第四阶段：数据迁移与旧逻辑清理

目标：删除历史包袱，但放在功能稳定之后执行。

### 迁移策略

- 如果 `admin` 表里有真实管理员账号，将其迁移到 `users` 表：
  - `username`
  - `password`
  - `role = ROLE_ADMIN`
  - `enabled = true`
  - 补齐必要字段，例如 `email`
- 确认迁移完成后，废弃：
  - `Admin` entity
  - `AdminRepository`
  - 独立 `AuthenticationService`
  - 启动时创建或重置默认 admin 的逻辑
- 是否删除 `admin` 表可以单独做数据库迁移，建议延后一个版本。

## 风险点

| 风险 | 说明 | 控制方式 |
|---|---|---|
| 登录状态丢失 | 改 localStorage key 会影响已登录用户 | 接受一次重新登录，或加临时兼容读取旧 key |
| 管理员无法登录 | 旧管理员只存在 `admin` 表 | 先写迁移脚本或保留兼容读取 |
| 房东权限异常 | 当前存在 `ROLE_HOST`、`ROLE_LANDLORD` 兼容逻辑 | 明确统一为 `ROLE_HOST`，短期保留 `ROLE_LANDLORD` 兼容 |
| 401 跳转重复 | 请求拦截器和路由守卫都可能处理 | 统一在 request 层清理状态，路由只做访问控制 |
| 默认 admin 密码问题 | 启动重置密码是高风险 | 第一批后端改动中先移除重置逻辑 |

## 测试清单

- 用户注册后自动登录。
- 用户登录后访问 `/user/profile`。
- 未登录访问 `/order/confirm` 跳转登录并带 redirect。
- 普通用户访问 `/host` 被拒绝。
- 房东访问 `/host` 成功。
- 管理员访问 `homestay-admin` 成功。
- 普通用户使用管理后台登录失败。
- 管理员 token 调用 `/api/admin/homestays` 成功。
- 普通用户 token 调用 `/api/admin/homestays` 返回 403。
- token 过期后请求受保护接口，前端清理状态并跳转登录。
- 同一浏览器同时登录前台和后台，互不覆盖。

## 回滚方案

- 第一阶段只改前台状态源，后端接口不动；若出问题，可以恢复旧 store 引用。
- 第二阶段只改管理后台 localStorage key；若出问题，可以临时兼容读取旧 `token`。
- 第三阶段保留 `/api/admin/auth/login` 接口路径，降低前端回滚成本。
- 第四阶段清理旧表和旧服务必须单独提交，不和核心认证改造混在一个提交里。

## 推荐执行顺序

1. 移除后端启动时重置默认 admin 密码的逻辑。
2. 前台合并 `auth` / `user` store。
3. 管理后台改用独立本地存储键。
4. `/api/admin/auth/login` 改为统一认证兼容入口，并校验 `ROLE_ADMIN`。
5. `CustomUserDetailsService` 收敛到只查 `users` 表。
6. 做管理员数据迁移。
7. 删除旧 `admin` 表相关代码。

## 工作量估算

| 阶段 | 估算 | 备注 |
|---|---:|---|
| 前台状态统一 | 1-2 小时 | 文件多，但逻辑直接 |
| 管理后台状态隔离 | 0.5-1 小时 | 主要是 key 和请求拦截器 |
| 后端统一认证 | 2-4 小时 | 需要谨慎处理管理员迁移和兼容 |
| 清理旧逻辑 | 1-2 小时 | 建议稳定后单独做 |
