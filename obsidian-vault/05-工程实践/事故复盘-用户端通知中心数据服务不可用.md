# 事故复盘-用户端通知中心数据服务不可用

> [!bug] 一句话结论
> 用户端个人中心打开通知中心时弹出“数据服务暂时不可用”，直接原因是后端读取 `notifications` 表时遇到当前 Java enum 不认识的历史枚举值，JPA 在业务转换前抛异常，接口被全局异常处理成 503。

## 一、问题现象

| 项目 | 说明 |
|------|------|
| 触发入口 | 用户端个人中心通知中心，后续也影响首页通知铃铛读取同一数据源 |
| 前端表现 | 页面弹出“数据服务暂时不可用” |
| 后端接口 | `GET /api/notifications` |
| 后端表现 | 全局异常处理捕获数据库访问异常，返回 503 |
| 当前修复 | 已补充 `EntityType.MESSAGE` 兼容历史数据，并重启本地 8080 后端服务 |

## 三、关键证据

### 3.1 后端日志

```text
No enum constant com.homestay3.homestaybackend.model.enums.EntityType.MESSAGE
```

该异常发生在 JPA 将数据库字符串反序列化成 Java enum 的阶段。也就是说，还没进入 `NotificationServiceImpl` 的 DTO 转换逻辑，接口就已经失败。

### 3.2 数据库现状

`notifications.entity_type` 的本地库统计：

| entity_type | 数量 |
|-------------|------|
| MESSAGE | 17136 |
| ORDER | 12331 |
| REVIEW | 2917 |

`notifications.type` 中存在订单状态或支付状态裸值：

| type | entity_type | 数量 |
|------|-------------|------|
| COMPLETED | ORDER | 5670 |
| PAID | ORDER | 1289 |
| PENDING | ORDER | 967 |
| CANCELLED_BY_USER | ORDER | 954 |
| CONFIRMED | ORDER | 951 |
| REFUNDED | ORDER | 774 |
| CANCELLED_BY_HOST | ORDER | 655 |
| CANCELLED | ORDER | 459 |

这些值能够解释为什么早期日志先报 `NotificationType.COMPLETED`、`PAID`，后续补齐后又暴露 `EntityType.MESSAGE`。

## 四、根因链路

```text
notifications 表长期保存历史通知
        ↓
type / entity_type 用字符串落库
        ↓
JPA 实体字段使用 Java enum 强绑定
        ↓
历史数据里出现当前 enum 没有的值
        ↓
Hibernate 读取列表时抛 IllegalArgumentException
        ↓
Spring Data 包装成数据库访问异常
        ↓
GlobalExceptionHandler 返回“数据服务暂时不可用”
        ↓
前端通知中心整体不可用
```

真正的问题不是单个 `MESSAGE` 值，而是通知模块把“历史事件数据”和“当前代码枚举”绑得过紧。

## 五、和订单“双状态”的关系

订单双状态本身是合理的：

| 字段 | 含义 | 示例 |
|------|------|------|
| `Order.status` | 订单履约状态 | `PENDING`、`CONFIRMED`、`CHECKED_IN`、`COMPLETED`、`CANCELLED` |
| `Order.paymentStatus` | 支付/退款状态 | `UNPAID`、`PAID`、`REFUND_PENDING`、`REFUNDED` |

问题出在通知事件模型没有和订单状态模型隔离。

| 正确边界 | 不应该发生的混用 |
|----------|------------------|
| 订单状态：`PAID` | 通知类型直接写成 `PAID` |
| 支付状态：`REFUNDED` | 通知类型直接写成 `REFUNDED` |
| 通知事件：`PAYMENT_RECEIVED` | 通知事件枚举镜像订单状态枚举 |
| 通知事件：`ORDER_COMPLETED` | 前端靠订单状态裸值识别通知类别 |

更准确的表达应该是：

```text
订单状态变化：UNPAID -> PAID
通知事件类型：PAYMENT_RECEIVED 或 ORDER_PAYMENT_SUCCEEDED
通知关联对象：entityType=ORDER, entityId=orderId
通知 payload：oldStatus、newStatus、oldPaymentStatus、newPaymentStatus
```

所以，订单双状态改动和这次问题有较强关联，但根因不是“双状态设计错了”。根因是双状态改动后，通知模块没有建立清晰的状态到事件的适配层，导致订单状态值污染了通知类型字段。

## 七、当前修复性质

| 修复 | 性质 | 说明 |
|------|------|------|
| 增加 `EntityType.MESSAGE` | 止血补丁 | 解决当前本地库已有的 `MESSAGE` 历史值 |
| `NotificationType` 增加订单状态兼容值 | 止血补丁 | 兼容历史通知中混入的订单状态裸值 |
| 前端通知中心统一 `notificationStore` | 局部治理 | 降低前端未读数和通知列表不同步问题 |
| enum converter 增加 `UNKNOWN` 兜底 | 读取侧防线 | 数据库出现未来未知值时，接口不会在 JPA 转换阶段直接失败 |
| 通知创建入口归一化 `type/entityType` | 写入侧治理 | 新通知保存前将 legacy alias 转为规范值，避免继续写入历史语义 |
| `NotificationDTO` 输出展示元数据 | 架构收口 | 后端承担通知分类、标题、跳转生成，前端减少重复推断 |
| Flyway 迁移 legacy 通知数据 | 数据治理 | 历史 `PAID/COMPLETED/PENDING/...` 与 `MESSAGE` 已有明确迁移路径 |

当前已经从止血推进到最小根治闭环：读取侧有 `UNKNOWN` 防线，写入侧会归一化，历史数据有 Flyway 迁移，前端不再主要依赖本地枚举推断。兼容枚举仍保留，作为历史数据和回滚期间的防御层。

## 八、值得反思的设计问题

### 8.1 持久化历史数据不应强依赖当前 enum

通知、消息、审计日志这类数据具有长期留存属性。今天写入的通知，半年后仍需要能打开。Java enum 代表当前代码版本的封闭集合，不适合直接成为历史数据读取成功的前置条件。

### 8.2 状态不是事件

订单状态描述“对象现在是什么状态”，通知类型应该描述“发生了什么事件”。二者相似但不是同一个概念。

| 概念 | 例子 |
|------|------|
| 订单状态 | `PAID` |
| 支付事件 | `PAYMENT_RECEIVED` |
| 订单状态 | `COMPLETED` |
| 通知事件 | `ORDER_COMPLETED` |

### 8.3 前端不应承担核心通知路由推断

当前前端按 `type/entityType/entityId` 推断图标、分类和跳转路径。更稳的做法是后端返回 `category`、`title`、`deepLink`、`payload`，前端只负责展示和跳转。

### 8.4 单条坏通知不应拖垮整个通知中心

通知中心是用户入口型功能，容错优先级高。单条异常历史数据最多应该显示为“系统通知”或被跳过，不应让整个列表 503。

## 十、建议的目标模型

```text
notification
- id
- recipient_user_id
- actor_user_id
- event_type          varchar，例如 PAYMENT_RECEIVED / ORDER_COMPLETED
- category            varchar，例如 order / message / review / system
- target_type         varchar，例如 ORDER / MESSAGE / REVIEW
- target_id           varchar
- title
- content
- deep_link           varchar，例如 /user/orders/123
- payload_json        json
- read_at
- deleted_at
- created_at
```

订单状态变化时：

```text
OrderStatusUpdater 更新 order.status/paymentStatus
        ↓
发布 OrderStatusChanged 领域事件
        ↓
OrderNotificationMapper 映射为通知事件
        ↓
NotificationService 保存站内通知
        ↓
WebSocketNotificationService 推送未读数或新通知
```
