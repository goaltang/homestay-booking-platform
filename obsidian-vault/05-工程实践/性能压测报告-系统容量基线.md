# 性能压测报告-系统容量基线

> [!summary] 一句话结论
> 在独立压测环境（MySQL 3307 + Redis 6380，5k 房源 / 30w 可用性 / 1w 订单）下，系统应用层远未到瓶颈：200→300 并发（VU）吞吐线性增长（155→232 req/s），列表 p95 仅 3.5→4.4ms、详情 p95 31→38ms、下单 p95 206→221ms，全部远低于预设阈值（500/800/1500ms）。真正触顶的是开发机硬件——400 VU（峰值 652 VU）时 WSL 8G 内存被压爆，后端进程被系统 SIGKILL。

## 一、测试目的与环境

| 项目 | 说明 |
|------|------|
| 目的 | 建立系统容量基线：确认当前架构在多大压力下仍达标，瓶颈在应用层还是硬件层 |
| 机器 | WSL 开发机，总内存 7.8G（swap 2G），CPU 共享宿主机 |
| 压测环境 | `docker-compose.perf.yml` 独立 MySQL 8.0(3307) + Redis 7(6380)，与开发库(3306)完全隔离 |
| 数据规模 | 5,000 房源（5 城市 × 1000）、1,002 用户（含 1000 压测住客）、300,000 可用性、10,000 历史订单 |
| 后端 | perf profile（`application-perf.properties`），端口 8082，ES 禁用（避免外部依赖），HikariCP 池 50 |
| 工具 | k6 v0.54.0（`tools/perf/load-test.js`），原始数据在 `tools/perf/reports/k6-result*.json` |

## 二、测试方法与场景

k6 三个场景贴近真实流量分布：

| 场景 | 流量占比 | 接口 | 预设 p95 阈值 |
|------|----------|------|---------------|
| 列表 list_heavy | 80% | `GET /api/homestays?cityCode=&page=0&size=20` | < 500ms |
| 详情 detail_mixed | 15% | `GET /api/homestays/{id}` | < 800ms |
| 下单 order_concurrent | 5% | `POST /api/orders`（登录 + 写库 + 分布式锁） | < 1500ms |

压力梯度：200 VU（基线）→ 300 VU → 400 VU（探上限），每轮约 2 分钟。

## 三、测试结果

### 3.1 200 VU 轮（基线）

总请求 18,975，吞吐 155 req/s，错误率 0.24%（阈值 <1% ✓）

| 场景 | 请求数 | avg | p50 | p90 | p95 | p99 | max |
|------|--------|-----|-----|-----|-----|-----|-----|
| 列表 | 9,045 | 2.4ms | 2.2ms | 3.1ms | 3.5ms | 5.7ms | 201ms |
| 详情 | 8,109 | 18.8ms | 19.6ms | 26.8ms | 30.7ms | 44.1ms | 220ms |
| 下单 | 1,821 | 110ms | 70ms | 138ms | 206ms | 1.38s | 2.4s |

下单成功 1,775 单；46 个业务拒绝（400）= 并发抢房冲突，防超卖锁正常拦截。

### 3.2 300 VU 轮

总请求 28,428，吞吐 232 req/s，错误率 0.72%（阈值内 ✓）

| 场景 | 请求数 | avg | p50 | p90 | p95 | p99 | max |
|------|--------|-----|-----|-----|-----|-----|-----|
| 列表 | 13,607 | 2.6ms | 2.3ms | 3.5ms | 4.4ms | 7.9ms | 162ms |
| 详情 | 12,103 | 25.9ms | 21.8ms | 31.4ms | 38.3ms | 215ms | 974ms |
| 下单 | 2,718 | 125ms | 73ms | 117ms | 221ms | 1.79s | 2.0s |

下单成功 2,438 单；205 个业务拒绝（并发冲突拦截）。

### 3.3 400 VU 轮（触顶事件）

峰值 652 VU 时 WSL 内存耗尽（swap 占用 900MB+），后端进程被系统 SIGKILL，压测后半段全部 `connection refused`，此轮数据无效，仅作为"硬件容量上限"证据。

### 3.4 两轮对比

| 指标 | 200 VU | 300 VU | 变化 |
|------|--------|--------|------|
| 吞吐 | 155 req/s | 232 req/s | +50% |
| 列表 p95 | 3.5ms | 4.4ms | 基本不变 |
| 详情 p95 | 30.7ms | 38.3ms | 小幅上升 |
| 详情 p99 | 44ms | 215ms | 长尾开始出现 |
| 下单 p95 | 206ms | 221ms | 基本持平 |
| 下单 p99 | 1.38s | 1.79s | 锁等待长尾 |
| 错误率 | 0.24% | 0.72% | 阈值内 |

## 四、结论与瓶颈分析

1. **应用层没有瓶颈**：并发翻 1.5 倍，吞吐线性增长，延迟轻微上升，全场景远低于阈值。列表在 300 并发下平均仍只要 2.6ms，说明 CPU/DB/缓存都游刃有余。
2. **当前真正的上限是硬件**：8G 内存的 WSL 开发机在 652 VU 时被压爆。要测应用层真实上限需更大机器或云环境。
3. **两个长尾观察（未来优化方向，目前未达阈值）**：
   - 详情 p99 44→215ms：高并发下 HikariCP 连接池（50）排队，属正常压力特征；
   - 下单 p99 ~1.8s：分布式锁等待 + 事务排队；205 个并发冲突被拦截恰好证明锁链路工作正常。
4. **环境限制（基线参考价值）**：ES 禁用（搜索链路未覆盖）、单机 WSL + Docker MySQL、登录未预热（压测脚本每 VU 首次登录，BCrypt 对比耗时，真实用户有 token 缓存，登录指标参考意义有限）。

## 五、过程发现：perf 套件 5 处修复（此前从未真正跑通过）

| # | 文件 | 问题 | 修复 |
|---|------|------|------|
| 1 | `application-perf.properties` | Flyway 迁移脚本不含主表(homestays/users) DDL，全新库从头迁移必失败 | 改 `ddl-auto=update` + `flyway.enabled=false`，由 Hibernate 建表（与 dev 结构一致） |
| 2 | `DatabaseHealthChecker.java` | 检查清单表名 `homestay_amenities` 与实体 JoinTable 实际名 `homestay_amenity` 不一致（误报） | 改为 `homestay_amenity` |
| 3 | `init-perf-data.sql` | availability 表旧列 `available` 已被 `status` + `locked` 取代 | INSERT 改 `status='AVAILABLE', locked=0` |
| 4 | `init-perf-data.sql` | 房源状态 `LISTED` 不在 `HomestayStatus` 枚举（DRAFT/PENDING/ACTIVE/INACTIVE/REJECTED/SUSPENDED），详情接口全 503 | 改 `ACTIVE` |
| 5 | `init-perf-data.sql` | 压测用户 BCrypt 哈希不匹配任何密码，登录全 401 | 用 `BCryptPasswordEncoder` 重新生成 123456 的哈希 |

> [!note] 复现提醒
> 压测后端必须禁用 devtools 自动重启（改 Java 代码会触发重启把压测后端搞挂）：`--spring.devtools.restart.enabled=false`；本机 8080 被其他服务占用，perf 后端用 `--server.port=8082`，k6 用 `BASE_URL` 环境变量覆盖。

## 六、复现方法

```bash
# 1. 起独立压测环境
cd /mnt/d/homestay3 && docker compose -f docker-compose.perf.yml up -d
# 2. 灌数据（约 25 分钟，30w 可用性）
docker exec -i homestay-mysql-perf mysql -uperf_user -pperf_pwd homestay_perf < tools/perf/data/init-perf-data.sql
# 3. 起后端（perf profile，8082，禁 devtools）
cd homestay-backend && mvn spring-boot:run -q -Dspring-boot.run.profiles=perf \
  -Dspring-boot.run.arguments="--server.port=8082 --spring.devtools.restart.enabled=false"
# 4. 压测（默认 200 VU；加码改 load-test.js 的 stages/rate）
cd /mnt/d/homestay3 && BASE_URL=http://127.0.0.1:8082 k6 run tools/perf/load-test.js
# 5. 清理
docker compose -f docker-compose.perf.yml down -v
```

## 七、2026-08-13 复测（D1-D3 安全/部署改造后回归 + ES N+1 修复）

> [!summary] 一句话结论
> 延迟指标全面持平或更优（列表 p95 3.8→3.0ms、详情 30.5→25.5ms、下单 p95 128→85ms、p99 1.38s→110ms），应用层无退化；吞吐 200VU 145.9 req/s（-6%）、300VU 177.6 req/s（-23%）的差距来自**环境内存压力**——本次压测期间 compose 全套（ES/MQ/后端/前端/Dify）+ perf 容器同机运行，可用内存仅 ~1G（08-09 基线压测时未跑 compose 全套）。再次验证基线结论：**瓶颈是开发机内存，不是应用层**。

### 背景
- D1：JWT 密钥轮换+环境变量化、异常处理 prod 隐藏、演示账号隔离
- D2：支付越权防护（createPayment 加订单归属校验）、status 收口登录态、mock-success @Profile 隔离
- D3：部署形态（Dockerfile + compose 全栈 + 空库初始化）
- ES N+1 修复：`homestayRepository.findAllById` → `findAllByIdIn`（`@EntityGraph("Homestay.withDetails")` 预取 owner/amenities/images），覆盖 ES 搜索路径 3 处 + HomestayGroupService 2 处 + UserFavoriteServiceImpl 1 处

### 结果对比（与 08-09 基线同条件：同脚本、同数据、perf profile、ES 禁用）

| 指标 | 200VU 基线(08-09) | 200VU 复测(08-13) | 300VU 基线 | 300VU 复测 |
|------|------|------|------|------|
| 吞吐 req/s | 155 | 145.9 (-6%) | 232 | 177.6 (-23%) |
| 错误率 | 0.24% | 0.99% | 0.72% | 1.14% |
| 列表 p95 | 3.5ms | 3.8ms | 4.4ms | 3.0ms |
| 详情 p95 | 30.7ms | 30.5ms | 38.3ms | 25.5ms |
| 下单 p95 | 206ms | 128ms | 221ms | 85ms |
| 下单 p99 | 1.38s | 1.37s | 1.79s | 110ms |

- 错误构成分析：400 全部为 order_concurrent 的并发下单冲突（防超卖锁正常拦截），200VU 下单成功率 89.4%、300VU 85.0%——**锁在工作**，非系统故障
- 环境注记：复测期间可用内存 ~1G（compose 全套+Dify+perf 同机），300VU 吞吐差距主要来源；延迟未受内存影响（缓存/GC 均正常）
