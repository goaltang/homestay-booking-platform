# 性能压测报告：首页统计接口串行 → 并行化对比

> 相关改造：`feat(perf): 首页统计五路 count 并行化`（CompletableFuture + taskExecutor）
> 配套工具：`tools/perf/`（独立 MySQL 3307 + Redis 6380，与开发库隔离）

## 一、背景

`HomeService.getStats()`（/api/home/stats 数据源）原实现**串行执行 5 个独立只读 count 查询**：
房源总数、覆盖城市数、评价总数、好评数、近 30 天订单数（+ availableToday 复用房源总数同口径查询）。

改造：5 路查询改为 `CompletableFuture.supplyAsync(..., taskExecutor)` 并行，`allOf().join()` 汇合，
异常语义不变（CompletionException 包装抛出），`@Cacheable("homeStats")`（Caffeine, 5min TTL）保留。

## 二、测试方法

- 环境：perf profile（MySQL 3307 homestay_perf，数据：5000 房源 / 1w+ 订单）+ 独立 Redis 6380
- 目标：**缓存 miss 场景**（并行化的收益点；命中场景由 Caffeine 兜底，与改造无关）
- 采样：重启后端（清 Caffeine）→ 用 /api/home/banners 探测就绪（不污染 homeStats 缓存）→
  立即请求 /api/home/stats 计时 → 重复 5 次取样本
- 样本单位：单请求总耗时（curl time_total）

## 三、结果

| 样本 | 串行（ms） | 并行（ms） |
|------|-----------|-----------|
| 1 | 50.0 | 49.8 |
| 2 | 45.3 | 34.5 |
| 3 | 47.9 | 43.0 |
| 4 | 104.9 | 37.9 |
| 5 | 84.6 | 34.8 |
| **中位数** | **50.0** | **37.9** |
| **P95** | **104.9** | **49.8** |
| **均值** | **66.5** | **40.0** |

**改善：中位 -24%，P95 -52%，均值 -40%**

## 四、结论与边界

1. **冷缓存 miss 场景长尾明显改善**（P95 105→50ms，-52%）——并行化把 5 次串行往返压成 1 次最长往返
2. **命中场景无差异**（Caffeine 本地缓存微秒级），首页 stats 有 5 分钟缓存，常态请求全部命中
3. **收益上限 = 最长单路查询耗时**（而非总耗时）：对本地快查询收益有限（本例 ~10-30ms），
   对远程调用/慢查询（如外部 API 聚合）收益会放大数倍——本改造更重要的意义是**建立了可复用的并行化模式**
4. 附加收益：`availableToday` 原为与房源总数同口径的重复 count，现复用并行结果，每请求少 1 次 DB 往返
5. 无回归：全量 424 用例全绿

## 五、并行化模式（后续复用）

```java
// 注入 AsyncConfig 的 taskExecutor，不要用 ForkJoinPool.commonPool（会与并行流争抢线程）
private final @Qualifier("taskExecutor") Executor taskExecutor;

CompletableFuture<X> f1 = CompletableFuture.supplyAsync(() -> repo.query1(), taskExecutor);
CompletableFuture<Y> f2 = CompletableFuture.supplyAsync(() -> repo.query2(), taskExecutor);
CompletableFuture.allOf(f1, f2).join();   // 任一失败抛 CompletionException，语义与串行一致
X x = f1.join();
```

适用判定：≥2 路独立 I/O、无顺序依赖、只读；不适用：CPU 密集计算（并行反而慢）、强顺序业务链。
